# freeMemory 적용 문제 보고서

## 결론

`freeMemory`가 해제한 메모리를 allocator가 다시 사용하지 못하던 직접 원인은 포인터 오프셋의 단위가 맞지 않은 것이다. `AS->ptr`는 `uint64_t` 배열이고 할당 결과도 배열 원소를 기준으로 계산되지만, 기존 해제 코드는 포인터를 정수 주소로 바꾼 뒤 빼서 바이트 오프셋을 얻었다. 이 값을 배열 인덱스와 비트 마스크 계산에 사용해 할당된 블록이 아닌 다른 위치를 지웠다.

또한 `upLevelingMask`는 자식 블록의 point 인덱스를 받는데, 기존 `getMemory`와 `freeMemory`는 절대 오프셋 `hendle`을 넘겼다. 그 결과 상위 레벨 요약 마스크도 잘못된 자식 위치를 반영할 수 있었다.

## 수정

- 포인터 오프셋을 `(uint64_t *)ptr - AS->ptr`로 계산해 배열 원소 단위로 맞췄다.
- 할당 및 해제 후 상위 마스크 갱신에 절대 오프셋 대신 블록의 `point`를 넘겼다.
- `tastFunction`에서 해제 직전 대상 비트가 모두 점유됐는지 확인하고, 해제 직후 그 비트가 전부 비었는지 단언하도록 했다.
- 해제 뒤 `FindMemory(AS, 32)`의 결과와 재할당 오프셋이 모두 `128`인지 검사하도록 했다.
- 테스트 함수 반환값을 `main`의 종료 코드와 연결해 실패를 프로세스 종료 상태에서도 감지하도록 했다.

## 검증

실행 명령:

```sh
gcc main.c -o main.e && ./main.e
```

검증 출력:

```text
[TEST] freed mask=...00000000000000000000000000000000
[TEST] FindMemory after free=128 expected=128
[TEST] reallocation offset=128 expected=128
[TEST PASS] freeMemory cleared the allocation and the allocator reused its offset
```

테스트는 기존 시나리오에서 두 번째 32 단위 할당이 시작한 원소 오프셋 `128`을 해제한다. 해제 후 해당 블록의 하위 32비트가 비워졌고, 검색과 다음 할당이 같은 `128`을 반환했다. 따라서 현재 재현 시나리오에서는 해제 마스크 변경과 실제 재사용이 모두 확인됐다.

## 범위와 남은 한계

이 결과는 현재 고정된 마스크와 32 단위 할당 재현에서의 검증이다. 여러 요청 크기와 블록 경계, 잘못된 포인터, 이중 해제, 전체 공간 고갈까지 allocator 전체의 정확성을 입증한 것은 아니다. 특히 `getMemory`의 할당 실패 시 반환 동작과 `freeMemory`의 입력 유효성 검사는 별도 테스트가 필요하다.
