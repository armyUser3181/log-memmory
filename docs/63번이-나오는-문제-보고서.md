# 63번 공간 반환 문제 분석 보고서

## 요약

`main.c`의 현재 테스트 경로에서 두 번째 `getAlloc(AS, 32)` 호출 결과로 기준 포인터와의 차이 `63`이 출력된다. 첫 번째 공간은 앞선 32 단위 할당으로 이미 가득 찬 상태다. 두 번째 공간에는 빈 비트가 남아 있지만, 요청된 32개가 연속해서 비어 있지는 않다.

```text
<point_any: 63, point_all: 2>
<gap: 63>
```

`63`은 빈 구간을 찾은 결과가 아니다. 두 번째 공간(point 1)에서는 요청 크기 32에 맞는 연속 후보가 없지만, 다음 공간(point 2)은 비어 있다. `ASFindBitRun`이 point 1에서 실패한 `-1`을 블록 오프셋에 더해 `63`으로 바꾸고, `any` 탐색은 이 잘못된 값을 유효 후보처럼 반환해 point 2로 진행하지 못한다.

## 재현

워크스페이스 루트에서 다음 명령으로 빌드하고 실행했다.

```sh
gcc -Wall -Wextra main.c -o /tmp/log-memmory-main
/tmp/log-memmory-main
```

테스트는 먼저 `getAlloc(AS, 32)`를 호출하고, 공간 구조를 두 번 확장한 뒤 `AS->ptr[ofMaskPoint8(1, 1)]`에 두 번째 공간의 점유 마스크를 직접 설정한 다음 두 번째 `getAlloc(AS, 32)`를 호출한다. 첫 번째 오프셋은 `30`이며, 첫 공간의 32개 비트를 채운다. 두 번째 마스크를 낮은 비트부터 해석하면 빈 인덱스는 `30..34`, `36..61`이다. 빈 비트는 총 31개 있지만, 최장 연속 구간은 26개이므로 32개 요청은 만족하지 않는다. 그런데 두 번째 반환 오프셋은 `63`으로 나온다. `rand()`를 쓰는 시간 측정은 검색 결과에 영향을 주지 않는다.

## 독립 검증 함수 실행

기존 `main`과 할당기 구현을 변경하지 않고, `tastFunction`만 재현·검증 함수로 바꿨다. 함수는 자체 allocator를 생성하고, 첫 할당이 `30`인지 확인한 다음 문제의 수동 마스크를 재현한다. 이어 point 1의 로컬 탐색 결과, point 2의 로컬 탐색 결과, 실제 `getAlloc` 오프셋을 각각 출력하고 기대 결과와 비교한다. 테스트 완료 후 allocator를 해제한다.

원래 프로그램의 `main`은 호출하지 않도록 별도 임시 실행기에서 `main` 이름만 바꿔 컴파일하고 `tastFunction`만 호출했다. 따라서 이 검증은 원래의 데모 실행 흐름과 분리되어 있고, 저장소에는 검증 함수 외의 실행 코드를 추가하지 않았다.

```text
[TEST] first allocation offset=30 expected=30
[TEST] point=1 result=63 expected=no candidate
[TEST] point=2 result=128 expected=128
[TEST] getAlloc offset=63 expected=128
[TEST FAIL] any search returned a local failure as an allocation instead of continuing
```

실패는 테스트 결함이 아니라 확인하려는 기존 버그를 검출한 결과다. point 1은 실패해야 하지만 63을 내고, point 2는 128을 내는데도 실제 `getAlloc`이 63을 반환한다. 함수는 이 불일치에서 `FLOW_ERROR`를 반환하고 별도 실행기도 종료 코드 1로 끝났다. 컴파일은 완료됐으며 기존 코드의 부호 비교, 연산자 우선순위, 미사용 값 관련 경고가 출력됐다.

## 동작 경로

1. 첫 번째 할당이 첫 공간의 32개 비트를 사용한다. 이후 테스트가 두 번째 공간의 점유 마스크를 직접 설정한다.
2. `FindMemory`의 `any` 경로가 두 번째 공간(`point=1`)을 조사해 `ASFindBitRun`을 호출한다.
3. `ASFindBitRun`에서 요청 크기 32로 `toBitRun`을 실행하지만, 연속 후보가 없어서 결과 `mask`는 `0`이다.
4. `ofLeftBit(mask)`는 `-1`을 반환한다. 그러나 함수는 실패 여부를 확인하지 않고 `ofLeftBit(mask) + (point << 6)`을 계산한다.
5. `point=1`일 때 unsigned 연산으로 `-1 + 64`가 `63`이 된다. `FindMemory`는 이 값을 유효 후보로 보고 반환한다. `any` 루프는 해당 level에서 현재 point를 한 번 검사하는 구조라 이 잘못된 값이 나온 뒤 다음 형제 point 2를 검사하지 않는다. 그 결과 `getAlloc`은 포인터 차이 `<gap: 63>`을 출력한다.

추가로 `any`의 실패 지점에서 point 2를 직접 `ASFindBitRun(AS, 1, 2, 32)`에 전달해 확인했다. point 2의 `all` 및 `any` 마스크는 모두 `0`이고, 같은 탐색 함수는 유효 후보 `128`을 반환했다. 이는 63의 직접 원인과 별개로, 현재 any 경로가 다음 공간을 시도하지 않는다는 점을 보여 준다.

## 원인 분석

### 직접 원인: 블록 내 탐색 실패값에 블록 오프셋을 더함

`ASFindBitRun`은 `mask == 0`인 경우에도 `ofLeftBit(mask) + (point << 6)`을 반환한다. `ofLeftBit(0)`은 unsigned `INT`의 `UINT64_MAX` 값이고, `point=1`의 블록 오프셋 64를 더하면 unsigned 래핑으로 63이 된다. 즉, 지역 탐색 실패가 전체 탐색 결과 `63`으로 변환된다.

이 테스트에서 두 번째 공간(point 1)에 빈 비트는 31개지만 32개 연속 빈 비트는 없다. point 1 자체에는 요청을 만족하는 후보가 없지만, 다음 공간(point 2)은 비어 있어 요청을 만족한다. 따라서 탐색은 point 1의 실패를 유지하고 다음 형제 공간을 시도해야 한다. 현재는 실패값이 63으로 바뀌면서 그 흐름이 끊긴다.

### 별도 위험: 실패 결과도 정상 포인터처럼 반환될 수 있음

`INT`는 `uint64_t` 별칭이며 `ofLeftBit`는 실패 시 `-1`을 반환한다. `getAlloc`은 `hendle == -1`인 경우에도 `NULL`을 반환하지 않는다. 마스크 갱신 인자로 `0`을 전달한 뒤 `hendle + AS->ptr`를 반환하므로, 탐색 실패가 호출자에게 명확히 전달되지 않고 잘못된 포인터가 만들어질 수 있다. 이것은 이번 로그의 `63`을 직접 만든 원인은 아니지만, 후보 탐색이 실패하거나 잘못될 때 증상을 키우는 문제다.

## 수정 방향

1. `ASFindBitRun`에서 후보 마스크가 0이면 블록 오프셋을 더하지 말고 명시적 실패 sentinel을 그대로 반환한다. 더 안전하게는 탐색 성공 여부와 인덱스를 별도 값으로 표현한다.
2. 현재 point의 연속 후보가 없을 때 상위 탐색 상태를 갱신해 다음 형제 point를 검사하도록 한다. 실패와 다음 후보 시도를 구분해 `63` 같은 래핑된 수를 탐색 상태로 사용하지 않는다.
3. `FindMemory`와 `getAlloc`이 최종 실패 sentinel을 유효 인덱스나 포인터로 처리하지 않도록 연결한다. 전체 공간이 고갈된 경우에만 `NULL`/오류를 반환하고, 실패 중에는 마스크 및 상위 요약을 변경하지 않는다.
4. 마스크를 직접 설정하는 현재 테스트를 유지하되, 결과는 작은 용량의 단순 선형 first-fit 기준 구현과 비교한다. 실제 할당/해제 경로를 통한 테스트도 별도로 추가한다.

## 확인할 회귀 테스트

- 두 번째 공간(point 1)의 현재 마스크에서 요청 크기 32를 탐색하면 후보 마스크가 0이므로 다음 형제 공간으로 진행해야 한다. 이 상태에서 63은 유효한 결과가 아니다.
- 다음 공간(point 2)이 비어 있을 때 요청 크기 32의 유효한 시작 위치를 반환한다.
- 모든 형제 공간에 32개 연속 빈 비트가 없을 때만 전체 검색 실패를 반환한다.
- 같은 총 빈 비트 수라도 조각나 최장 구간이 32보다 짧으면 실패를 반환한다.
- 실패 후 `getAlloc`이 `NULL`/오류를 반환하고 마스크나 상위 요약을 변경하지 않는지 확인한다.
- 요청 크기 `1`, `32`, `63`, `64`, `65`와 경계에 걸친 연속 구간을 기준 선형 탐색과 비교한다.

## 검증 범위와 주의

위 재현은 현재 하드코딩된 테스트 상태에서 `point=1`, `size=32`, 후보 `mask=0`, `ofLeftBit(mask)=-1`, 최종 덧셈 결과 `63`임을 GDB와 독립 검증 함수로 확인했다. point 1에는 요청을 만족하는 연속 구간이 없지만, 다음 point 2에는 유효한 요청 공간이 있고 시작 오프셋은 128이다. 그럼에도 `any` 경로와 `getAlloc`은 63을 반환한다. 이 보고서는 할당기 전체의 정확성을 증명하지 않는다.
