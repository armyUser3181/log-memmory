# 63번 문제 수정 결론

## 결론

이번 수정은 보고된 32 단위 요청의 `63` 반환 문제에 대해 **의미 있는 효과가 확인됐다**. 수정 전에는 point 1에서 연속 빈 공간을 찾지 못한 결과가 블록 오프셋과 합쳐져 `63`으로 변환됐다. 현재 코드는 `ASFindBitRun`에서 비트 탐색 결과를 먼저 확인하고, 실패 인덱스 `-1`에는 블록 오프셋을 더하지 않는다. `FindMemory`의 `any` 경로도 sentinel을 다음 탐색 호출로 전달하지 않도록 방어한다.

현재 실행 결과는 다음과 같다.

```text
[TEST] point=1 result=-1 expected=no candidate
[TEST] point=2 result=128 expected=128
[TEST] getAlloc offset=128 expected=128
[TEST PASS] any search skipped the fragmented block and used the next block
[TEST] third allocation offset=160 expected=160
```

즉, point 1에서의 지역 실패가 더 이상 유효 인덱스 `63`으로 오인되지 않고, 다음 비어 있는 point 2의 시작 위치 `128`이 실제 할당 결과로 반환된다. 이어지는 32 단위 할당도 `160`을 반환해 이 재현 상태에서는 순차 할당도 기대대로 진행됐다.

## 확인한 수정 지점

- `ASFindBitRun` 반환 계산: 이전 코드는 `ofLeftBit(mask) + (point << 6)`을 바로 반환했다. `mask == 0`이면 `ofLeftBit`가 unsigned `-1`을 내고, point 1의 64 오프셋을 더하는 과정에서 63으로 래핑됐다. 현재 코드는 먼저 `index`를 구하고, `index == -1`이면 블록 오프셋을 더하지 않는다. 그래서 point 1의 직접 탐색 결과가 63이 아닌 `-1`로 보존된다.
- `FindMemory`의 `any` 하향 탐색: 이전에는 `ASFindBitRun`을 무조건 호출했다. 현재는 `point_any == -1`일 때 호출을 건너뛰어 실패 sentinel이 다른 인덱스 계산으로 흘러가지 않도록 한다.
- `SYSTEM.FLOW.ERROR_EVENT` 진단: `ASFindBitRun` 입력, 원시 마스크, `toBitRun` 결과, 인덱스를 조건부로 출력한다. 이 코드는 관찰용이며 탐색 결과를 바꾸지는 않는다.
- `tastFunction`: 외부 allocator를 받던 기존 시험 코드를 자체 allocator를 만드는 검증 함수로 바꾸고, `main`에서 호출하도록 변경했다. 테스트는 초기 용량에서 네 번 확장한다. 이전 데모는 두 번 확장했으므로, 이 테스트는 단순히 기존 실행을 반복한 것이 아니라 더 깊은 계층을 활성화하는 설정 변경도 포함한다.

## 실제 `any` 경로

GDB로 두 번째 32 단위 할당 시점의 `FindMemory` 반환 직전 값을 확인했다.

```text
index_any = 128
index_all = -1
return = 128
```

따라서 이 실행에서 `getAlloc(AS, 32)`가 128을 반환한 것은 `all` 후보로 대체한 결과가 아니다. `any` 경로가 직접 128을 선택했다. 그 선택은 `FindMemory`의 64개 자식 후보 검사에서 만들어진다.

```text
workLevel = 2
low = 1
point_any = 0
mask = 0xfffffffffffffffc
```

이 마스크의 첫 set bit는 2다. 즉, 중간 레벨 검사가 point 0과 point 1을 후보에서 제외하고 point 2를 선택한다. 이어 `ASFindBitRun`이 point 2의 완전히 빈 마스크에서 로컬 인덱스 0을 찾아 전체 시작 인덱스 `0 + (2 << 6) = 128`을 만든다. 반면 point 1을 직접 검사한 진단 호출은 `mask=0`, `index=-1`을 반환해 실패 sentinel 보존도 별도로 확인됐다.

### 효과 판단의 범위

두 부분의 역할을 구분해야 한다. 실패 인덱스의 오프셋 래핑을 막은 것은 직접 버그 수정이다. 현재 재현에서 다음 블록을 찾은 것은 네 번 확장해 중간 레벨의 64개 자식 후보 검사를 활성화한 탐색 경로다. 이전 두 번 확장 설정과 현재 네 번 확장 설정은 동일한 조건이 아니므로, 현재 통과 결과만으로 동일한 원래 용량에서의 동작까지 입증했다고 보아서는 안 된다. 다만 직접 point 1 검사가 `63`에서 `-1`로 바뀐 사실과, 현재 확장 조건에서 `any`가 point 2를 선택해 실제 128을 반환한 사실은 각각 확인됐다.

## 추가 테스트 결과 해석

현재 함수는 네 번째 할당에 대해 다음을 출력한다.

```text
[TEST] fourth allocation offset=100 expected=192
```

이는 16 단위 요청의 새 실패가 아니다. point 1에는 32 단위 요청을 만족하지 못해 남겨둔 26비트 연속 빈 구간이 있고, 그 구간의 시작 위치가 `64 + 36 = 100`이다. 16 단위 요청은 그 구간에 들어가므로 `100`은 유효한 위치다. 따라서 `expected=192`라는 기대값이 테스트 상태와 맞지 않는다. 현재 검증 코드는 이 값이 `-1`인지 여부만 검사하기 때문에 100을 실패로 판정하지는 않지만, 출력의 기대값은 수정하거나 해당 비교를 올바르게 추가할 필요가 있다.

## 검증 신뢰도와 남은 범위

핵심 회귀 사례는 실행 결과로 통과했다. 다만 현재 `main`은 `tastFunction()`의 반환값을 무시하고 항상 `0`을 반환한다. 따라서 테스트 로그에 실패가 출력되어도 프로세스 종료 코드만으로는 실패를 감지하지 못한다. 또한 이번 검증은 하드코딩된 마스크와 32 단위 요청을 중심으로 한 단일 재현이며, 모든 레벨·요청 크기·경계 조건의 정확성을 증명하지는 않는다.

따라서 판정은 다음과 같다.

- **63 반환 재현 수정:** 확인됨
- **다음 빈 블록 탐색:** 현재 재현에서 확인됨 (`128`)
- **이어지는 32 단위 할당:** 확인됨 (`160`)
- **16 단위 테스트의 기대값:** 잘못 설정됨 (`100`이 유효, `192`는 현재 상태에서 근거 없음)
- **전체 할당기 정확성:** 미검증
- **프로세스 종료 코드 기반 테스트 실패 감지:** 미완성
