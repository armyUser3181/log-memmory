# 63번 문제 수정 결론

## 결론

이번 수정은 보고된 32 단위 요청의 `63` 반환 문제에 대해 **의미 있는 효과가 확인됐다**. 수정 전에는 point 1에서 연속 빈 공간을 찾지 못한 결과가 블록 오프셋과 합쳐져 `63`으로 변환됐다. 현재 코드는 `ASFindBitRun`에서 비트 탐색 결과를 먼저 확인하고, 실패 인덱스 `-1`에는 블록 오프셋을 더하지 않는다. `FindMemory`의 `any` 경로도 sentinel을 다음 탐색 호출로 전달하지 않도록 방어한다.

현재 실행 결과는 다음과 같다.

```text
[TEST] point=1 result=-1 expected=no candidate
[TEST] point=2 result=128 expected=128
[TEST] getAlloc offset=128 expected=128
[TEST PASS] any search skipped the fragmented block and used the next block
[TEST] third allocation offset=160 expected=160
```

즉, point 1에서의 지역 실패가 더 이상 유효 인덱스 `63`으로 오인되지 않고, 다음 비어 있는 point 2의 시작 위치 `128`이 실제 할당 결과로 반환된다. 이어지는 32 단위 할당도 `160`을 반환해 이 재현 상태에서는 순차 할당도 기대대로 진행됐다.

## 확인한 수정 지점

- `ASFindBitRun`: `ofLeftBit(mask)` 결과가 `-1`인지 먼저 판단해 실패값에 `(point << 6)` 오프셋을 합산하지 않는다.
- `FindMemory`의 `any` 하향 탐색: 현재 point가 실패 sentinel이면 `ASFindBitRun`을 호출하지 않아 실패 상태가 정수 인덱스로 다시 변형되지 않게 한다.
- `tastFunction`: 자체 allocator를 만들고 문제의 점유 패턴을 구성해 point 1 실패, point 2 성공, 실제 `getAlloc` 결과를 비교한다.

## 추가 테스트 결과 해석

현재 함수는 네 번째 할당에 대해 다음을 출력한다.

```text
[TEST] fourth allocation offset=100 expected=192
```

이는 16 단위 요청의 새 실패가 아니다. point 1에는 32 단위 요청을 만족하지 못해 남겨둔 26비트 연속 빈 구간이 있고, 그 구간의 시작 위치가 `64 + 36 = 100`이다. 16 단위 요청은 그 구간에 들어가므로 `100`은 유효한 위치다. 따라서 `expected=192`라는 기대값이 테스트 상태와 맞지 않는다. 현재 검증 코드는 이 값이 `-1`인지 여부만 검사하기 때문에 100을 실패로 판정하지는 않지만, 출력의 기대값은 수정하거나 해당 비교를 올바르게 추가할 필요가 있다.

## 검증 신뢰도와 남은 범위

핵심 회귀 사례는 실행 결과로 통과했다. 다만 현재 `main`은 `tastFunction()`의 반환값을 무시하고 항상 `0`을 반환한다. 따라서 테스트 로그에 실패가 출력되어도 프로세스 종료 코드만으로는 실패를 감지하지 못한다. 또한 이번 검증은 하드코딩된 마스크와 32 단위 요청을 중심으로 한 단일 재현이며, 모든 레벨·요청 크기·경계 조건의 정확성을 증명하지는 않는다.

따라서 판정은 다음과 같다.

- **63 반환 재현 수정:** 확인됨
- **다음 빈 블록 탐색:** 현재 재현에서 확인됨 (`128`)
- **이어지는 32 단위 할당:** 확인됨 (`160`)
- **16 단위 테스트의 기대값:** 잘못 설정됨 (`100`이 유효, `192`는 현재 상태에서 근거 없음)
- **전체 할당기 정확성:** 미검증
- **프로세스 종료 코드 기반 테스트 실패 감지:** 미완성
